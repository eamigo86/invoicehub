# RFC 0006 — Applied AI

**Status:** draft

The AI acts through tools that call the same services as the UI, with the permissions of the user who uses it; it never issues or sends an invoice without confirmation. Models are consumed via OpenRouter behind a custom adapter.

## v1 use cases

| Case | Example | Technique |
| --- | --- | --- |
| Create invoice from text | "Invoice Acme for 20 h of consulting at $90 and the March hosting" | Structured output validated with Pydantic → draft |
| Questions about the data | "Who owes me for more than 60 days?" | Tool calling over read-only queries |
| Explain a doubtful reconciliation | "Why is this payment marked ambiguous?" | Context with the remitmatch breakdown |
| Suggest tax or product | When typing a free-form line | Classification with a cheap model |
| External agents | Claude Desktop or another client managing invoices | MCP server with the same tools |

## LLM adapter

```python
from typing import Protocol, TypeVar

from pydantic import BaseModel

T = TypeVar("T", bound=BaseModel)


class LLMClient(Protocol):
    """Provider-agnostic interface the rest of the app depends on."""

    def complete_structured(self, messages: list[dict], schema: type[T], *, model: str) -> T:
        """Return a response parsed and validated into ``schema``.

        Implementations request JSON-schema output when the model supports it,
        otherwise validate with Pydantic and retry once with the error message.

        Args:
            messages: Chat messages in OpenAI format.
            schema: Pydantic model describing the expected output.
            model: OpenRouter model id.

        Returns:
            A validated instance of ``schema``.
        """
        ...

    def run_tools(
        self, messages: list[dict], tools: list["Tool"], *, model: str, max_steps: int = 6
    ) -> str:
        """Run a tool-calling loop until the model answers or ``max_steps`` is hit.

        Args:
            messages: Conversation so far.
            tools: Tools the current user is allowed to call.
            model: OpenRouter model id.
            max_steps: Upper bound on tool calls per turn.

        Returns:
            The model's final text answer.
        """
        ...
```

`OpenRouterClient` implements the protocol with OpenRouter's OpenAI-compatible API. Each call records model, tokens, cost and latency per tenant.

## Tools

- Read: `search_invoices`, `get_invoice`, `list_overdue`, `get_customer`, `explain_match`.
- Write: `create_draft_invoice`, `add_invoice_line`. Issuing, sending and applying payments are **not** tools: they require a user click.
- Each tool receives its context (tenant, user, role) from the server, never from the model's arguments, and goes through the permissions service.

## MCP server

It exposes the same tools with the official MCP SDK for Python, authenticated with per-tenant API tokens with scopes (RFC 0002). It serves as an agent integration demo.

## Evals and cost

- **Evals in CI:** a set of 30–50 cases (text → expected invoice, question → expected answer) with per-field scoring. A prompt or model change that lowers the score breaks the build.
- **Cost:** cheap model by default and a more capable one only for complex tool calling; monthly budget per tenant and a global cap in the demo.
- **Dashboard:** cost, p50/p95 latency and error rate per use case.

## Security

- Bank descriptions, customer names and notes are untrusted data: they go to the model delimited as data and cannot expand permissions or trigger actions without confirmation.
- No data from other tenants in the context; the isolation tests (RFC 0002) also cover the tools.
- Every AI action is recorded in the audit log with actor `ai` and the user who requested it.

## Alternatives considered

| Alternative | Why it was rejected |
| --- | --- |
| Single-provider SDK | Ties the project to one model; OpenRouter allows comparing models in the evals |
| Agent frameworks (LangChain and similar) | Too much abstraction for a simple tool-calling loop; custom code is easier to explain in an interview |
| RAG over the invoices | The data is structured: tool-based queries are more exact than semantic search |
